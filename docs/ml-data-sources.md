# ML Data Sources

## Overview

Two public synthetic datasets acquired for ML training and evaluation. Both are synthetically generated — neither contains real customer or payment data.

## Dataset 1: ReconRiver (Primary)

| Field | Value |
|-------|-------|
| Dataset | ReconRiver synthetic reconciliation dataset |
| Source | https://huggingface.co/datasets/heybadrinath/reconriver-synthetic-reconciliation |
| License | CC-BY-4.0 |
| Original Size | 70,088 rows across 4 scenario packs |
| Local Size | 34 files, ~12MB total |
| Purpose | Primary reconciliation training data — payment-to-obligation matching with ground truth |
| Ground Truth | YES — 24,259 labeled reconciliation outcomes with 15 outcome types and 20 reason codes |
| Synthetic | YES — generated by Java 21 dataset generator with SYNTH- prefix identifiers |
| Attribution | Required under CC-BY-4.0 |

### Why This Is Primary

ReconRiver provides exactly what Settle needs:
1. **Internal transactions** (our `payment_events` equivalent) with order IDs, amounts, currencies, statuses
2. **Processor transactions** (our Razorpay equivalent) with processor event types, fees, net amounts, settlement batches
3. **Bank settlements** with credited amounts and bank references
4. **Ground truth** linking all three via merchant_order_id, with expected outcomes (MATCHED, AMOUNT_MISMATCH, MISSING_PROCESSOR, DUPLICATE, etc.)

This maps directly to Settle's 6 demo scenarios:
- Exact reference match → L1_EXACT_ORDER_MATCH
- Partial payment → PARTIAL_REFUND / L1_PARTIAL_REFUND_LINK
- Missing reference → MISSING_PROCESSOR / L1_MISSING_PROCESSOR
- Overpayment → AMOUNT_MISMATCH / L1_GROSS_AMOUNT_EQUALITY
- Duplicate event → DUPLICATE_PROCESSOR / L1_DUPLICATE_PROCESSOR
- Late settlement → LATE_SETTLEMENT / L2_SETTLEMENT_WINDOW

### Key Identifiers for Joining

```
internal_transactions.internal_payment_id ↔ processor_transactions.merchant_order_id
processor_transactions.settlement_batch_id ↔ bank_settlements.settlement_batch_id
expected_reconciliation.internal_payment_id ↔ internal_transactions.internal_payment_id
expected_reconciliation.processor_transaction_id ↔ processor_transactions.processor_transaction_id
expected_reconciliation.bank_entry_id ↔ bank_settlements.bank_entry_id
```

## Dataset 2: FreeFinancialTransactions50M (Supporting)

| Field | Value |
|-------|-------|
| Dataset | FreeFinancialTransactions50M |
| Source | https://huggingface.co/datasets/ziadatalabs/FreeFinancialTransactions50M |
| License | CC-BY-NC-4.0 |
| Original Size | 50,000,000 rows (1.5GB parquet) |
| Local Subset | 40,004 rows (3.5MB CSV) |
| Purpose | Supporting transaction data — realistic transaction patterns, amounts, currencies, categories |
| Ground Truth | NO — standalone transactions, no invoice/order/obligation linking |
| Synthetic | YES — generated synthetic financial transactions |
| Attribution | Required under CC-BY-NC-4.0 (non-commercial use only) |

### Why This Is Supporting

The 50M dataset provides:
1. **Realistic transaction distributions** — 8 transaction types, 4 statuses, 6 currencies, 14 merchant categories
2. **Amount variation** — right-skewed distribution (median $30, mean $55, max $3,455)
3. **Temporal spread** — 31 months of data (2024-01 to 2026-07)
4. **Scale** — 50M rows demonstrates the approach works at volume

However, it CANNOT be used for reconciliation training because:
- No invoice/order IDs to link transactions to obligations
- No payment-to-invoice ground truth
- No processor/bank settlement data
- No reconciliation outcomes

### Intended Use

Use the 50M sample to:
- Validate feature extraction handles realistic transaction distributions
- Test amount-ratio and currency features across a wide range of values
- Ensure the model doesn't overfit to ReconRiver's specific patterns
- Stress-test the feature pipeline at scale

Do NOT use the 50M sample to:
- Train reconciliation matching (no ground truth)
- Evaluate matching accuracy (no labels)
- Generate synthetic obligations (no order/invoice structure)

## Limitations

### Both Datasets Are Synthetic

Neither dataset contains real financial data. This means:
- Transaction patterns may not match real payment behavior
- Amount distributions may differ from actual merchant transactions
- Exception rates are designed for demos, not statistical realism
- Customer behavior is not modeled

### Implications for ML Training

1. **Models trained on synthetic data may not generalize to real payments** — this is acceptable for a hackathon demo
2. **Feature importance may differ in production** — real payment data has different patterns
3. **Confidence calibration may be off** — synthetic data produces cleaner separation than real data
4. **The 50M dataset's non-commercial license** restricts production use — acceptable for hackathon

### What Would Be Needed for Production

For a production Settle deployment, you would need:
1. Real payment processor data (Razorpay transaction logs)
2. Real internal ledger data (merchant order records)
3. Real bank settlement data (bank statements)
4. Human-labeled ground truth (which transactions matched which orders)
5. Temporal train/test splits (no future data leakage)
